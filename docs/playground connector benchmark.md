# playground connector benchmark

🏎️ Benchmark the throughput of a connector

Measures how many records per second a running self managed connector  
processes, so that two runs can be compared: another `--connector-tag`,  
another batch size, another number of tasks. Everything runs on one  
docker host, so the numbers are relative: compare runs on the same  
machine only.

🎓 Tip: playground run `--benchmark` runs it right after the example (also  
a toggle in the playground run menu).

`--mode` drain (default) pauses the connector, loads a backlog of  
`--nb-records`, resumes the connector and measures the time it takes to  
process the backlog. This is the most reproducible number, since it does  
not depend on how fast the load is generated.

`--mode` steady measures the throughput during `--duration` (after  
`--warmup`), while `--stream-load-command` runs in the background. When the  
connector simply keeps up with the load (consumer lag of a sink, records  
generated by the load of a source), the summary says so: the result is  
then the speed of the load, not of the connector.

⏱️ For a source connector, `--mode` steady also measures the end-to-end  
latency of the records: kafka record timestamp - time of the change in  
the source system (a field of the value). After the measure, the  
benchmark reads the records written to the topics of the connector  
during it (all of them up to 100000, a sample spread over the measure  
otherwise), and the summary, the result json and the report give its  
p50 / p95 / p99 / max (over time, distribution, slowest records), also  
in the comparable runs and the `--connector-tag` comparisons. When the  
connector simply keeps up with the load, this is the number to compare.  
The field is `--latency-field`, or the one the load writes the time of  
the change to (create_ts of the CUSTOMERS table, update_ts with `--shape`  
update), or source.ts_ms of a CDC envelope (commit time in the  
database), or wallTime / clusterTime of a MongoDB change event. It is  
not measured in a drain, where the latency of a record is the time it  
waited in the backlog.

The load comes from the example:

- sink connectors: the `playground topic produce` of the example

script that feeds the connector is replayed with `--nb-messages`  
`<n>` (same schema, key and headers), so every sink example that  
produces its data works without anything else

- source connectors: benchmark-load.bash next to the example

script, called with `--records` `<n>` `--mode` preload|stream `--shape`  
bulk|small-txn|update (rows in the CUSTOMERS table for the  
postgres, mysql, oracle and sql server examples, documents for  
mongodb, messages for ibm mq, mqtt, activemq, sqs, kinesis,  
pub/sub and cloudwatch logs, files for spool dir, filepulse,  
filestream, sftp, ftps, hdfs 2 / 3 and the generalized s3, gcs and  
azure blob storage sources, see the README of the example). It is  
called with `--check` first, so that an unsupported  
combination fails before the connector is paused

- or `--load-command` / `--stream-load-command`, which take precedence

`BENCHMARK_LOAD_SCRIPT`=`<file>` uses another load script than  
benchmark-load.bash: a file name in the folder of the example (or an  
absolute path), e.g. one per reproduction model named after its ticket  
(`BENCHMARK_LOAD_SCRIPT`=benchmark-load-123456.bash). It takes the same  
arguments, and `--enable-sql-datagen` uses it too.

Throughput is read from the connect JMX metrics of the tasks  
(sink-record-read-total: records read from kafka, including the ones  
filtered or sent to the dlq; source-record-write-total), sampled every  
`--interval`. Results are written to `--output-dir` (samples csv, result  
json and an html report with the charts, opened in the browser at the  
end in an interactive terminal) and appended to the benchmark-history  
file, and the summary compares them with the previous benchmark of the  
same connector in the same example (or with `--compare` `<result json>`).

Each result records the setup it ran on (host cpu and memory, container  
engine resources, connect image and whether it is emulated, jvm and  
heap, number of workers and brokers, environment, connector config with  
secrets masked): the report shows it, and the summary warns when the  
previous run was on a different setup.

🛩️ The connect workers are recorded with Java Flight Recorder during  
the measure (over JMX: the cp images have no jcmd, nothing is  
restarted), and the report and the summary say where the time of the  
task threads went: running, blocked on the system behind the  
connector, in the Kafka client, locks, waits; the CPU by layer  
(connector, converters, SMTs, Kafka client, libraries, logging), hot  
methods, allocation, GC, exceptions, with findings and next steps.  
With `--connector-tag`, the versions are compared the same way. The  
recording costs a few % of throughput: `--no-flight-recorder` disables  
it, and the summary warns when the previous run was not recorded the  
same way. The .jfr files are kept in `--output-dir` (JDK Mission  
Control, or playground analyze flight-recorder).

📊 When Grafana runs (example started with `--enable-jmx-grafana`,  
or `--enable-sql-datagen`), the measure is annotated on the Kafka  
Connect, connector (Debezium, Oracle CDC, XStream, MongoDB) and  
Kafka cluster dashboards, and the summary and the report link to  
them at the time of the run (each version is annotated with  
`--connector-tag`). Grafana is not started by the benchmark: its  
JMX exporter and containers use CPU, and the summary warns when  
the previous run was not measured the same way.

☁️ Fully managed source connectors (ccloud/fm-\*-source examples that  
ship a benchmark-load.bash, the one of the equivalent self managed  
example: same local database or broker, reached by the connector  
through ngrok): the records are counted from the end offsets of the  
topics of the connector every `--interval` (its kafka.topic or  
topic.prefix, and the topics consumed by the example script,  
`--topic` to choose them), since Confluent Cloud gives no JMX: no batch  
time, running ratio, cpu, gc, flight recorder nor `--connector-tag`.  
A drain starts measuring at the first records seen after the resume  
(Confluent Cloud takes a few seconds to restart the tasks, and its  
status lags behind them), so the records seen by that first sample  
are not measured. The throughput includes the network between the  
docker host and Confluent Cloud. Run the example and answer n when it asks to  
delete the connector, then run the benchmark.

☁️ Fully managed sink connectors: the load is the replay of the  
`playground topic produce` of the example, like for a self managed  
sink, and the records are counted from the offsets committed by the  
consumer group of the connector (connect-`<lcc id>`). Confluent Cloud  
commits them about every minute, so the end of a drain is known  
within one commit interval: a drain that sees less than 5 commits  
is reported as a lower bound, and the summary gives the  
`--nb-records` of a drain of 10 commits (within ~10%, usually 1M  
records or more).

📈 After the measure of a fully managed connector, the benchmark  
reads its per minute metrics in the Confluent Cloud Metrics API  
(sent_records / received_records, exact counts published about 30s  
into each minute): the steady throughput is the median of the full  
minutes of the measure (a drain of 3 minutes or more has one), which  
does not depend on when a sink commits its offsets, and the put batch  
time, batch size and dlq records fill the rows that JMX gives for a  
self managed connector. The Metrics API uses the Cloud API key  
(`CONFLUENT_CLOUD_API_KEY`) and does not answer for a deleted connector.

⚠️ Not available with the cfk environment yet.

## Usage

```bash
playground connector benchmark [OPTIONS]
```

## Environment Variables

#### `BENCHMARK_LOAD_SCRIPT`

📜 Load script to use instead of benchmark-load.bash: a file of the example folder, or an absolute path

## Options

#### `--verbose, -v`

🐞 Show command being ran.

#### `--connector, -c CONNECTOR`

🔗 Connector name

🎓 Tip: not needed when only one connector is running

#### `--mode MODE`

🏁 drain (time to process a backlog of `--nb-records`) or steady (throughput during `--duration`)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `drain`
| Allowed Values: | `drain`, `steady`

#### `--nb-records NB-RECORDS`

💯 Number of records of the backlog in drain mode (default is 100000)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `100000`

#### `--shape SHAPE`

🧱 Shape of the load, passed to benchmark-load.bash (default is bulk)

- bulk: one transaction with all the records
- small-txn: one transaction per record
- update: updates existing records
- delete: deletes existing records (drain only; not for a JDBC source, which does not capture deletes; with Debezium or XStream, each deleted row also gives a tombstone, unless tombstones.on.delete=false)

A sequence of shapes, e.g. bulk,update,delete, runs one drain per shape on the same rows (insert, update, then delete them) and compares the phases in the summary and the report. Drain of a source connector only.

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `bulk`

#### `--record-size RECORD-SIZE`

🏋️ Record size in bytes, passed to benchmark-load.bash (default is 0: size given by the load)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `0`

#### `--load-command LOAD-COMMAND`

📥 Command that loads the backlog in drain mode, instead of benchmark-load.bash (or of the replayed produce of a sink)

It runs with bash -c, from the current directory, while the connector is paused. It must create the records and return: `--nb-records` is then the number of records the connector should process, unless the command prints a line `BENCHMARK_RECORDS`=`<n>`.

Examples:

# sink: 1M records in the topic of the connector (use the schema of its records)  
`--nb-records` 1000000 `--load-command` `playground topic produce -t my-topic --nb-messages 1000000 --value @predefined-schemas/avro/customer.avsc`

# source: your own script, which inserts the rows and prints `BENCHMARK_RECORDS`=`<n>`  
`--load-command` "./load-my-table.sh 500000"

#### `--stream-load-command STREAM-LOAD-COMMAND`

🌊 Command that generates load continuously in steady mode, instead of benchmark-load.bash (or of the replayed produce of a sink)

It runs in the background with bash -c, from the current directory. At the end of the measure, the file named by the `BENCHMARK_STOP_FILE` environment variable is created: the command should stop at the end of its current batch when it exists. It is killed after 120s otherwise, and killing a producer in the middle of a batch can send a truncated record to the topic. If it prints `BENCHMARK_BATCH`=`<records>` `<epoch seconds>` after each batch, the summary tells when the connector only kept up with the load.

Example, batches of 10000 records in the topic of the connector until the end of the measure:

- `--stream-load-command` 'while [ ! -f "\`$BENCHMARK_STOP_FILE`" ]; do playground topic produce -t my-topic `--nb-messages` 10000 `--value` @predefined-schemas/avro/customer.avsc; echo "`BENCHMARK_BATCH`=10000 \$(date +%s)"; done'

A line `BENCHMARK_LATENCY_FIELD`=`<field>` tells which field of the records of a source holds the time of the change, for the end-to-end latency (see `--latency-field`).

#### `--topic, -t TOPIC`

🗳 Topics to count records in at the end of a drain, to check the result of a source connector (default is the topics of the connector)

| Attributes      | &nbsp;
|-----------------|-------------
| Repeatable:     |  ✓ Yes

#### `--duration DURATION`

⏱️ Duration of the measure in steady mode, in seconds or with a s/m/h suffix (default is 5m)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `5m`

#### `--warmup WARMUP`

🔥 Time excluded from the measure at the beginning in steady mode (default is 30s)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `30s`

#### `--interval INTERVAL`

🔁 Interval between samples (default is 5s)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `5s`

#### `--max-wait MAX-WAIT`

⏳ Max time to wait for the backlog to be processed in drain mode (default is 30m)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `30m`

#### `--connector-tag CONNECTOR-TAG`

🧩 Benchmark these versions of the connector plugin one after the other (repeat the flag), and compare them

For each version: playground update-version `--connector-tag` (only the connect container is restarted, the connector and its offsets are kept), check that the connector runs the requested version, an untimed warm-up drain (the worker jvm was restarted), then the benchmark. The original version is restored at the end, and the summary and the report compare the versions.

Example: `--connector-tag` 10.8.4 `--connector-tag` 10.9.9

⚠️ A downgrade or a major version change can be incompatible with the offsets or the config of the connector: the benchmark stops at the first FAILED state.

| Attributes      | &nbsp;
|-----------------|-------------
| Repeatable:     |  ✓ Yes

#### `--rounds ROUNDS`

🔁 With `--connector-tag`, number of rounds over the versions (default is 1): 2 alternates them (A B A B), which shows a drift from one run to the next

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `1`

#### `--output-dir OUTPUT-DIR`

📂 Folder for the samples csv, the result json and the html report (default is /tmp/playground-benchmark)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `/tmp/playground-benchmark`

#### `--compare COMPARE`

⚖️ Result json of a previous benchmark to compare with (default is the previous benchmark of the same connector in the same example, from the benchmark-history file)

#### `--no-history`

🙈 Do not append the result to the benchmark-history file

#### `--sessions SESSIONS`

🧵 Run the benchmark-load.bash of the example in `<sessions>` parallel sessions (default is 1)

A drain splits `--nb-records` between them, steady mode gives each session batches of `--nb-records`. Concurrent transactions are what a busy database looks like to a CDC connector (interleaved transactions in the redo log or the WAL, several open transactions). Only with the benchmark-load.bash of the example, not with `--load-command`.

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `1`

#### `--no-flight-recorder`

🛩️ Do not record the connect workers with Java Flight Recorder during the measure (no "where the time goes" section in the report)

The recording costs a few % of throughput: compare runs recorded the same way.

#### `--latency-field LATENCY-FIELD`

⏱️ Field of the records of a source connector that holds the time of the change in the source system, for the end-to-end latency measured in `--mode` steady (kafka record timestamp - this field)

A dotted path for a nested field (after.create_ts, source.ts_ms), matched case insensitively, through avro unions. Its value can be an epoch in s, ms, µs or ns, an ISO-8601 string, or a MongoDB date or timestamp.

Default: the field the load writes the time of the change to (`BENCHMARK_LATENCY_FIELD` printed by benchmark-load.bash: create_ts of the CUSTOMERS table, update_ts with `--shape` update), otherwise source.ts_ms of a CDC envelope (commit time in the database), wallTime or clusterTime of a MongoDB change event.

🎓 Tip: use a column with milliseconds (TIMESTAMP(3)), and `--shape` small-txn: with `--shape` bulk, a default `CURRENT_TIMESTAMP` is the start of the transaction of the whole batch.

| Attributes      | &nbsp;
|-----------------|-------------
| Conflicts With: | `--no-latency`

#### `--no-latency`

🙈 Do not measure the end-to-end latency of a source connector in `--mode` steady (it reads the records of the measure after it)

| Attributes      | &nbsp;
|-----------------|-------------
| Conflicts With: | `--latency-field`

#### `--json`

📄 Print the result as json instead of the summary

## Examples

```bash
playground connector benchmark --connector filestream-sink --nb-records 3000000
```

```bash
playground connector benchmark --connector jdbc-postgres-source --nb-records 1000000 --shape small-txn
```

```bash
playground connector benchmark --mode steady --duration 2m --warmup 20s
```

```bash
playground connector benchmark --connector debezium-postgres-source --mode steady --duration 2m --shape small-txn --latency-field after.create_ts
```

```bash
playground connector benchmark --nb-records 1000000 --load-command "playground topic produce -t my-topic --nb-messages 1000000 --value @predefined-schemas/avro/customer.avsc"
```

```bash
playground connector benchmark --mode steady --duration 2m --stream-load-command 'while [ ! -f "$BENCHMARK_STOP_FILE" ]; do playground topic produce -t my-topic --nb-messages 10000 --value @predefined-schemas/avro/customer.avsc; echo "BENCHMARK_BATCH=10000 $(date +%s)"; done'
```

```bash
playground connector benchmark --load-command "./my-load.sh" --json
```

```bash
playground connector benchmark --nb-records 1000000 --connector-tag 10.8.4 --connector-tag 10.9.9 --rounds 2
```

```bash
playground connector benchmark --nb-records 1000000 --no-flight-recorder
```

```bash
playground connector benchmark --nb-records 1000000 --shape small-txn --sessions 5
```

```bash
playground connector benchmark --nb-records 500000 --shape bulk,update,delete
```
