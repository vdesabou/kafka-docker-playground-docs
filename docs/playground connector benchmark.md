# playground connector benchmark

🏎️ Benchmark the throughput of a connector

Measures how many records per second a running self managed connector  
processes, so that two runs can be compared: another `--connector-tag`,  
another batch size, another number of tasks. Everything runs on one  
docker host, so the numbers are relative: compare runs on the same  
machine only.

`--mode` drain (default) pauses the connector, loads a backlog of  
`--nb-records`, resumes the connector and measures the time it takes to  
process the backlog. This is the most reproducible number, since it does  
not depend on how fast the load is generated.

`--mode` steady measures the throughput during `--duration` (after  
`--warmup`), while `--stream-load-command` runs in the background. When the  
connector simply keeps up with the load (consumer lag of a sink, records  
generated by the load of a source), the summary says so: the result is  
then the speed of the load, not of the connector.

The load comes from the example:

- sink connectors: the `playground topic produce` of the example

script that feeds the connector is replayed with `--nb-messages`  
`<n>` (same schema, key and headers), so every sink example that  
produces its data works without anything else

- source connectors: benchmark-load.bash next to the example

script, called with `--records` `<n>` `--mode` preload|stream `--shape`  
bulk|small-txn|update (rows in the CUSTOMERS table for the  
postgres, mysql, oracle and sql server examples, documents for  
mongodb, messages for ibm mq and mqtt, see the README of the  
example). It is called with `--check` first, so that an unsupported  
combination fails before the connector is paused

- or `--load-command` / `--stream-load-command`, which take precedence

Throughput is read from the connect JMX metrics of the tasks  
(sink-record-read-total: records read from kafka, including the ones  
filtered or sent to the dlq; source-record-write-total), sampled every  
`--interval`. Results are written to `--output-dir` (samples csv, result  
json and an html report with the charts, opened in the browser at the  
end in an interactive terminal) and appended to the benchmark-history  
file, and the summary compares them with the previous benchmark of the  
same connector in the same example (or with `--compare` `<result json>`).

⚠️ Not available for fully managed connectors and the cfk environment yet.

## Usage

```bash
playground connector benchmark [OPTIONS]
```

## Options

#### `--verbose, -v`

🐞 Show command being ran.

#### `--connector, -c CONNECTOR`

🔗 Connector name

🎓 Tip: not needed when only one connector is running

#### `--mode MODE`

🏁 drain (time to process a backlog of `--nb-records`) or steady (throughput during `--duration`)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `drain`
| Allowed Values: | `drain`, `steady`

#### `--nb-records NB-RECORDS`

💯 Number of records of the backlog in drain mode (default is 100000)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `100000`

#### `--shape SHAPE`

🧱 Shape of the load, passed to benchmark-load.bash (default is bulk)

- bulk: one transaction with all the records
- small-txn: one transaction per record
- update: updates existing records

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `bulk`
| Allowed Values: | `bulk`, `small-txn`, `update`

#### `--record-size RECORD-SIZE`

🏋️ Record size in bytes, passed to benchmark-load.bash (default is 0: size given by the load)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `0`

#### `--load-command LOAD-COMMAND`

📥 Command that loads the backlog in drain mode, instead of benchmark-load.bash (or of the replayed produce of a sink)

It runs with bash -c, from the current directory, while the connector is paused. It must create the records and return: `--nb-records` is then the number of records the connector should process, unless the command prints a line `BENCHMARK_RECORDS`=`<n>`.

Examples:

# sink: 1M records in the topic of the connector, with the schema of its records on stdin  
`--nb-records` 1000000 `--load-command` `playground topic produce -t my-topic --nb-messages 1000000 < my-schema.avsc`

# source: your own script, which inserts the rows and prints `BENCHMARK_RECORDS`=`<n>`  
`--load-command` "./load-my-table.sh 500000"

#### `--stream-load-command STREAM-LOAD-COMMAND`

🌊 Command that generates load continuously in steady mode, instead of benchmark-load.bash (or of the replayed produce of a sink)

It runs in the background with bash -c, from the current directory. At the end of the measure, the file named by the `BENCHMARK_STOP_FILE` environment variable is created: the command should stop at the end of its current batch when it exists. It is killed after 120s otherwise, and killing a producer in the middle of a batch can send a truncated record to the topic. If it prints `BENCHMARK_BATCH`=`<records>` `<epoch seconds>` after each batch, the summary tells when the connector only kept up with the load.

Example, batches of 10000 records in the topic of the connector until the end of the measure:

- `--stream-load-command` 'while [ ! -f "\`$BENCHMARK_STOP_FILE`" ]; do playground topic produce -t my-topic `--nb-messages` 10000 \< my-schema.avsc; echo "`BENCHMARK_BATCH`=10000 \$(date +%s)"; done'

#### `--topic, -t TOPIC`

🗳 Topics to count records in at the end of a drain, to check the result of a source connector (default is the topics of the connector)

| Attributes      | &nbsp;
|-----------------|-------------
| Repeatable:     |  ✓ Yes

#### `--duration DURATION`

⏱️ Duration of the measure in steady mode, in seconds or with a s/m/h suffix (default is 5m)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `5m`

#### `--warmup WARMUP`

🔥 Time excluded from the measure at the beginning in steady mode (default is 30s)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `30s`

#### `--interval INTERVAL`

🔁 Interval between samples (default is 5s)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `5s`

#### `--max-wait MAX-WAIT`

⏳ Max time to wait for the backlog to be processed in drain mode (default is 30m)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `30m`

#### `--output-dir OUTPUT-DIR`

📂 Folder for the samples csv, the result json and the html report (default is /tmp/playground-benchmark)

| Attributes      | &nbsp;
|-----------------|-------------
| Default Value:  | `/tmp/playground-benchmark`

#### `--compare COMPARE`

⚖️ Result json of a previous benchmark to compare with (default is the previous benchmark of the same connector in the same example, from the benchmark-history file)

#### `--no-history`

🙈 Do not append the result to the benchmark-history file

#### `--json`

📄 Print the result as json instead of the summary

## Examples

```bash
playground connector benchmark --connector filestream-sink --nb-records 3000000
```

```bash
playground connector benchmark --connector jdbc-postgres-source --nb-records 1000000 --shape small-txn
```

```bash
playground connector benchmark --mode steady --duration 2m --warmup 20s
```

```bash
playground connector benchmark --nb-records 1000000 --load-command "playground topic produce -t my-topic --nb-messages 1000000 < my-schema.avsc"
```

```bash
playground connector benchmark --mode steady --duration 2m --stream-load-command 'while [ ! -f "$BENCHMARK_STOP_FILE" ]; do playground topic produce -t my-topic --nb-messages 10000 < my-schema.avsc; echo "BENCHMARK_BATCH=10000 $(date +%s)"; done'
```

```bash
playground connector benchmark --load-command "./my-load.sh" --json
```
